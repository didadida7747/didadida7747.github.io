# 01 - 快速上手 OMP

目标：在一个具体项目中完成一次可检查的任务闭环。先从文档修改、小脚本提示优化或单一 bug 修复开始，不要拿重要生产仓库作为试验场。

## 1. 在正确目录启动

```powershell
cd D:\path\to\your-project
git status
omp
```

`git status` 的作用是让你知道开始前有哪些改动。若工作区已有重要未提交内容，先处理或记录它们，避免把原有改动误认为 OMP 的结果。

## 2. 第一轮：理解项目

```text
先只读，不要修改。请读取项目说明、目录结构、包管理或构建文件、测试配置和项目规则；指出最小验证命令，以及为完成下面任务必须读取的文件：
<写入你的任务>
```

## 3. 第二轮：限定范围的小改动

```text
请只修改以下范围：
<文件或目录>

目标：
<一个具体、可验收的目标>

要求：
1. 先说明准备修改的文件和理由；
2. 不要进行无关重构，也不要新增依赖；
3. 完成后运行最小相关验证；
4. 报告改动文件、验证结果和未验证风险。
```

## 4. 第三轮：单独检查

不要立即追加功能，先输入：

```text
进入检查阶段，不要再实现新功能。
请检查本次改动的 diff，确认是否有无关文件、敏感信息或不必要依赖；运行相关测试/构建/静态检查。最后分开报告：已验证、未验证、剩余风险。
```

然后由你在终端复核：

```powershell
git diff --stat
git diff
```

## 5. 陌生错误的处理顺序

1. 要求它贴出错误来源的文件、命令和关键输出，不要让它猜。
2. 让它解释最小复现与假设，再决定是否修改。
3. 一次只验证一个修复方向。
4. 若涉及嵌入式硬件、串口、网络、数据库或部署，明确区分本机静态检查、构建通过和真实环境验证。

## 6. 什么时候停止并人工接管

- 准备删除大量文件、改迁移脚本、改权限或提交/推送。
- 要求输入敏感凭据或访问无关目录。
- 连续两次修复没有缩小问题范围。
- 你无法解释它的改动为什么正确。

这时保留 diff、错误和当前状态，回到更小的任务或用另一个工具做独立审查。
