# AI 编程工具选择指南

更新时间：2026-08-13

这个目录保留三套互补的本地学习资料：Codex、Grok Build 和 Oh My Pi（OMP）。它们都能阅读项目、修改文件和运行命令，但并不是同一种产品。选择时先看任务需要的工作流和账号/模型边界，再看模型本身。

## 先给结论

| 当前情况 | 优先选择 | 原因 |
|---|---|---|
| 要完成一个明确的工程任务，重视读项目、最小改动、验证和任务记录 | Codex | 产品工作流完整，桌面端、CLI、项目任务和审查体验连贯 |
| 已在终端使用 Grok Build，且希望直接使用已有 Grok 配置/模型 | Grok Build | 配置和习惯已建立，适合在项目目录快速处理开发任务 |
| 要在多个模型或 API 提供商之间切换、比较或设置故障回退 | OMP | 开源多模型代理壳，路由与扩展能力强 |
| 只是问一个概念、写一小段文本或没有明确工程目录 | 不急着开代理 | 先用普通聊天确认问题；需要读写文件和验证时再进入项目目录 |

默认选择：对日常学习项目，先用 **Codex**；已有 Grok Build 配置并希望用 Grok 时用 **Grok Build**；只有明确需要多模型、路由、LSP/DAP 或研究代理框架时，再投入时间配置 **OMP**。

## 三者分别是什么

| 工具 | 定位 | 模型与账号 | 主要优势 | 主要代价 |
|---|---|---|---|---|
| Codex | OpenAI 的编程代理产品，提供 App、CLI 等入口 | OpenAI/Codex 账号和官方能力 | 任务、项目、改动检查与验证衔接好；入门路径清晰 | 模型选择与运行环境的可定制程度不以“多供应商路由”为目标 |
| Grok Build | xAI/Grok 的终端编程代理 | Grok/xAI 或当前已配 relay | 已有本机配置，终端直接启动；有技能、MCP、计划等工作流 | 主要绑定 Grok 生态；复杂任务仍需自己控制权限和验证 |
| OMP | 开源的终端 AI 编程代理框架 | 自行登录或配置兼容的模型/API 提供商 | 可多模型、多供应商、回退链；内置 LSP、调试、子代理、扩展 | 配置与费用边界由你负责；需要理解 API 凭据、权限和实际模型差异 |

重要：OMP 是“运行代理的工具壳”，不是一个独立大模型。把 GPT、Grok 或其他模型接入 OMP，通常仍受相应服务的账号、权限、地区、额度和 API 计费约束。现有 ChatGPT/Codex 或 Grok 订阅是否可用于 OMP，以登录方式和各服务当前政策为准；不要自行假设订阅可替代 API 额度。

## 按任务选择

### 1. 学习 STM32、ROS2 或一个陌生仓库

优先 Codex 或 Grok Build。第一轮只读项目，要求其列出目录、构建命令、硬件/环境前提和不确定项；确认后再改一小步。涉及板子、串口、接线、传感器时，AI 的“代码已改”不等于硬件已验证，仍要保留实测证据。

### 2. 修一个具体 bug、补文档或做小功能

哪个工具已经在正确项目目录、账号也正常，就用哪个。提示中写清目标、改动范围、不能碰的文件和最小验证命令。不要为了工具切换而重复配置。

### 3. 想比较 Grok、GPT、Claude、Gemini 等模型在同一仓库的表现

选择 OMP。它适合把“代理工具能力”与“模型能力”拆开比较。先用一个小而可验收的任务、固定提示词和测试命令比较；不要只凭一次对话的文风判断强弱。成本、数据发送范围与凭据存储方式要先确认。

### 4. 想把重复工程流程固化下来

优先 Codex 的 `AGENTS.md`、Skills 或现有项目约束；Grok Build 可沿用 skill 与规格化模板；OMP 可读取多种已有规则格式并进一步扩展。无论选哪一个，规则文件只保留稳定的项目事实、测试命令和安全限制，不要把密钥写入其中。

### 5. 需要并行审查、子代理或调试器

OMP 的特色更集中在多模型路由、LSP/DAP、子代理和可扩展运行时。先在可回滚的小仓库试用，确认模型、权限、用量和工作树行为后再用于主项目。普通学习任务不需要为了这些功能而强行上 OMP。

## 共同的安全闭环

无论选谁，都按同一顺序工作：

1. 在目标项目目录启动，并先只读理解项目。
2. 写清目标、范围、不做什么和验收标准。
3. 先小步修改，避免把“顺手重构”混进任务。
4. 查看实际 diff，运行最小相关的测试、构建或静态检查。
5. 区分“代码检查通过”和“硬件/线上环境已验证”。
6. 绝不把 API Key、Token、密码、私钥或个人数据贴进提示词、仓库或文档。
