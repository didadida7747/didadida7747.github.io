# 05 · 子代理与 Task 工具：上下文隔离的艺术

> Task 是 Claude Code 工具箱里最特殊的一个：调用它不会干活，而是**再启动一个完整的 Agent**。
> 本篇拆这个"套娃"设计。Anthropic 的多代理研究系统博客是理解它的最好参照。

## 一、Task 工具的工作方式

```
主 Agent（上下文 A）
   │ 调用 Task(prompt="在代码库里找到所有处理支付超时的位置，返回文件:行号列表")
   ▼
子 Agent（全新上下文 B：干净 + 自己的系统提示词 + 工具）
   │ 疯狂干活：读 40 个文件、跑 15 次搜索……
   │ 这些过程全部留在上下文 B 里
   ▼
   把最终消息（比如 20 行结论）作为工具结果返回给主 Agent 的上下文 A
```

【一句话本质】**Task 的返回值 = 子 Agent 的最后一条消息**。过程不回流。

## 二、为什么这个设计值钱：三个收益

### 收益 1：上下文隔离（核心价值）

主线需要的是"支付超时在哪些文件"这个结论，不需要"读了 40 个文件产生的 15 万 token 过程"。没有 Task 工具的话，这些垃圾全堆在主线，几轮下来窗口爆掉、注意力稀释。

类比：老板（主 Agent）需要的是调研报告的**一页纸结论**，而不是实习生（子 Agent）的全部浏览器历史。

### 收益 2：并行

多个 Task 可以同时派出（架构调研、文档调研、测试现状各一个子代理）。子代理在各自独立上下文里互不干扰。

【注意】并行的真正收益不是省时间，而是**"搜索空间可以暴力化"**——同时开 4 个方向找线索，主线最后只负责汇聚判断。Anthropic 多代理研究系统博客给过一个震撼数字：多代理系统在评估中比单代理 baseline 的 token 消耗高约 **15 倍**，但换来的是显著的性能提升——**token 换智力，在研究型任务是划算的**。

### 收益 3：专业化（自定义子代理）

`.claude/agents/code-reviewer.md` 这样的文件可以定义专属子代理：独立系统提示词、限定工具集、指定模型。比如：

```markdown
---
name: code-reviewer
description: 代码审查专家。写完代码后主动调用
tools: Read, Grep, Glob, Bash   # 只给只读工具，从物理上防它乱改
model: sonnet
---
你是严格的代码审查员……（专属人设与检查清单）
```

【为什么这个设计好】把"角色分工"从提示词技巧升级成了**配置化的实体**：每个人设有自己的上下文、自己的权限、自己的模型档位。这就是操作系统的"进程"思想：隔离 + 调度 + 权限。

## 三、三个反直觉的设计决策

### 1. 为什么子代理默认拿不到对话历史？

子 Agent 的初始上下文只有：自己的系统提示词 + 你在 prompt 参数里写的话。主线的对话历史不传进去。

【为什么】传历史 = 隔离失效 = 回到上下文污染的老路。代价是你必须学会**给子代理写自包含的任务书**（它是空降兵，不知道背景）。这也解释了为什么 Task 的 prompt 参数描述里要求"必须包含任务所需的全部上下文"。

### 2. 为什么子代理数量要克制？

多代理的隐性成本：
- token 成本倍增（每个子代理自带固定开销的上下文）
- 信息在"压缩→传递"中失真（子代理转述时丢了主线才知道的约束）
- 协调复杂度（多个结论冲突时主线要当仲裁）

Anthropic 博客里给出的努力分级经验：简单事实查找 1 个代理 3-10 次工具调用；复杂研究 2-4 个子代理；超过这个规模收益急剧递减。**多代理不是越大越好，是"不得已才开"。**

### 3. 为什么子代理也用同一个循环？

子 Agent 内部就是一个标准的 Agent 主循环（01 篇）。**递归复用同一个内核**，而不是为子代理发明新机制——这是工程设计里的"自相似"原则：一个正确的抽象，在各层级重复使用，维护成本最低。

## 四、你该怎么用：主线的分工原则

| 任务类型 | 给主线还是子代理 | 理由 |
|---|---|---|
| 大范围探索（找实现、调研架构） | 子代理 | 过程垃圾多，结论小 |
| 精确修改（改某个函数） | 主线 | 需要完整上下文连续性 |
| 独立验证（跑测试、代码审查） | 子代理 | 视角隔离反而更客观 |
| 多方案对比实验 | 子代理（并行） | 各试各的，最后汇总 |

【实用技巧】给子代理下任务时，用"返回格式约束"提高汇聚质量：*"返回：1) 文件:行号列表 2) 每处一句话说明 3) 你不确定的点"*。让返回值本身就是结构化的。

## 思考题

1. 如果子 Agent 干到一半发现任务前提是错的（主线给的需求有误），它该怎么办？harness 层面有没有更好的机制？（对照你自己的工作流想想"向上反馈"怎么做）
2. 多代理系统的"信息失真"问题，除了"约束返回格式"，你还能想到什么解法？（提示：让子代理把过程写到文件里，主线按需去读——这正是很多高级玩法的核心）
3. 什么时候应该用"同一个子代理分多轮干"而不是"开多个子代理"？
