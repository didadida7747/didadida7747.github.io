# 个人能力盘点与转型路线图

## 1. 定位与总原则

### 你的当前定位
- 身份：电子信息工程本科在读，基础课成绩不差，技术上处于从“会做题”向“会做项目”过渡阶段。
- 主线方向：先入行嵌入式，再向具身智能过渡。
- 现实约束：不以极限保研为第一目标，采取“技术优先，成绩守线”的策略。
- 资源条件：每周可投入 `20+ 小时`，有板子和电脑，可以使用较强 API 模型和 agent 工具。

### 核心判断
- 你现在最缺的不是“知道更多内容”，而是 `工程闭环`、`稳定输出`、`可验证成果`。
- 你现在不该盲目跟风“跑模型”，而该先把 `编程基础 + 嵌入式项目能力 + 工程习惯 + AI 工具力` 接起来。
- 你真正要建立的是一条连续路径：

`刷题式学习 -> 模块化写代码 -> 做完整项目 -> 会调试和复盘 -> 用 AI 提效 -> 补机器人/控制/ROS -> 转具身智能`

## 3. 最该优先补的 5 个点

### 1. 项目闭环能力
这是你当前最危险的短板。你已经有输入，但缺“从需求到交付”的完整回路。

验收标准：
- 能独立做完 1 个综合 STM32 项目。
- 有能运行的代码、接线说明、模块说明、调试日志。
- 能讲清楚你遇到过哪些 bug、怎么定位、怎么修。

### 2. 模块化 C 与工程代码组织
你不是不会写代码，而是还没有把代码组织成工程。

验收标准：
- 能把一个项目分成 `bsp / drivers / services / app` 或类似层次。
- 能写 `.h/.c` 接口，减少复制粘贴。
- 能让别人通过目录结构快速看懂项目。

### 3. 调试与排障方法
嵌入式最值钱的能力之一不是“会背寄存器”，而是“出问题能定位”。

验收标准：
- 能独立排查至少 5 类常见问题：
  - 时钟配置错误
  - GPIO 配置错误
  - 中断未触发
  - 串口收发异常
  - 定时器周期不对
- 每次排查都能留下简短记录。

### 4. AI / agent 的结构化使用
你已经具备入口条件，但还没把 AI 真正变成工具链。

验收标准：
- 能写 3 个可复用 prompt 模板：
  - 学习型提问模板
  - 调试型提问模板
  - 代码审查型提问模板
- 能让 agent 完成一次“小任务拆分 -> 输出结果 -> 你验收修正”的闭环。

### 5. 数学与机器人方向前置图谱
这块要开始了解，但不能喧宾夺主。

验收标准：
- 能用自己的话讲清：
  - 具身智能为什么需要控制、感知和系统工程
  - 嵌入式能力在机器人里能用在哪里
  - 未来要补哪些课，而不是只会说“学 AI”

## 4. 分阶段路线

## 近 2 个月：现在到大二上前

### 核心目标
把“学过 STM32 外设”升级为“做成 1 个像样的小系统”。

### 主要任务
- 完成 1 个综合 STM32 项目。
- 每周固定补最小工程基础：`Git + Linux 命令行 + 模块化 C + 调试方法`。
- 为 AI 建立最小工作流，而不是无目的聊天。

### 综合项目建议
优先选你现在已经在做的项目，不换题，避免重新开坑。

项目至少包含：
- `3-5 个外设协同`
- `一个清晰的主流程或状态机`
- `异常处理或边界处理`
- `日志/串口打印辅助调试`
- `README + 接线说明 + 模块说明 + bug 记录`

如果你当前项目太散，可收敛到以下类型之一：
- 多传感器采集 + OLED/串口显示系统
- 智能小车的简化控制板程序
- 温湿度/光照/按键/蜂鸣器/显示联动的监控系统

### 每周节奏
- `3 天`：主项目开发与联调
- `2 天`：补工程基础与复盘
- `1 天`：整理文档、总结 bug、完善 AI 模板
- `1 天`：机动补漏或休息

### 近 2 个月验收
- 不看教程能从空工程搭出主框架。
- 能清楚解释每个模块的职责。
- 能独立定位至少 5 类常见 bug。
- 有一个能给学长或同学展示的项目版本。

## 5. AI 使用规范

### 适合让 AI 帮你的场景
- 帮你解释一个外设或协议的关键机制
- 帮你检查模块划分是否合理
- 帮你列调试思路、测试点和边界情况
- 帮你做代码审查，指出风险和命名问题
- 帮你总结学习笔记、整理复盘模板

### 不适合直接交给 AI 的场景
- 你还没自己思考就直接要完整代码
- 你还没自己定位就直接把 bug 整体外包
- 你还没读过手册，就让 AI 替你理解所有底层细节
- 你拿到答案后不验证，直接复制到工程里

### 推荐提问模板

#### 学习型
```text
我在做一个 STM32 项目，当前模块是【模块名】。
我已经知道【我已知的内容】。
我不理解的是【具体问题】。
请用“原理 -> 常见错误 -> 我该怎么验证”的结构回答，不要直接给完整代码。
```

#### 调试型
```text
我现在遇到的现象是【具体现象】。
已知条件：芯片/外设/配置/接线/预期行为分别是【内容】。
我已经排查了【已排查项】。
请按“最可能原因排序 + 每一步该观察什么现象 + 如何缩小范围”回答。
```

#### 代码审查型
```text
这是我的 STM32 模块代码，目标是【目标】。
请不要重写全部代码，而是重点检查：
1. 模块边界是否清晰
2. 命名和接口是否合理
3. 是否有潜在 bug
4. 有没有更适合我当前水平的小改进
```

### AI 成本控制规则
- 难题、架构题、复盘题：用强模型。
- 查概念、改文案、整理表格：用便宜模型。
- 所有高成本调用都要带明确目标，避免闲聊式消耗。

### AI 使用底线
- `先自己想 15-30 分钟，再问 AI`
- `先给出现象和已排查项，再问 AI`
- `先验证答案，再接收答案`
- `所有 AI 生成代码都要自己能解释`

## 6. 每个阶段的验收方式

### 你是否真的进步了，看这 6 条
- 能不能不看教程写出项目主框架。
- 能不能解释模块为什么这么拆。
- 能不能独立定位常见 bug。
- 能不能把学过的内容沉淀成自己的模块和文档。
- 能不能看懂并改动一部分别人的代码。
- 能不能把 AI 当工具，而不是答案生成器。

### 明确的失败信号
- 看了很多资料，但还是拿不出一个完整项目。
- 每次写代码都必须依赖教程逐行照搬。
- 遇到 bug 只会换代码，不会定位问题。
- 聊了很多 AI，但没有形成模板、流程或产出。
- 被“别人已经跑模型”带乱，导致当前主线被打散。

## 7. 你现在最强、最危险、最该暂缓的点

### 当前最强的点
- 愿意投入，能长期学习。
- 方向感明确，知道自己不想只停留在做题。
- 已经开始用 AI 辅助学习，这比很多人起点更靠前。

### 当前最危险的点

- 技术主线容易被焦虑打断。
- 基础虽然不差，但还没有经过项目和调试的“锻打”。

### 当前应暂缓的点
- 大规模追模型训练和“跑大 AI 项目”
- 过早追求复杂 skill 体系或花哨自动化
- 在没有稳定项目输出前投入太多时间研究高阶框架
