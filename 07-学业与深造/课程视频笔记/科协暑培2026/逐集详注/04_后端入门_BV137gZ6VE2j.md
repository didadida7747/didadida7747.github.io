## 知识整理

### API 路由与 HTTP 基础

前后端交互一句话：客户端发 HTTP 请求（浏览器 JS 发出、DNS 解析找服务器），后端处理完业务逻辑按协议返回 JSON。"method 和 URL 表达你想干什么，状态码则表示这件事有没有干成，二者各司其职。"路由匹配靠 method + URL：GET 查询 / POST 创建 / PUT 全量更新 / PATCH 部分更新 / DELETE 删除。状态码四族：2xx 成功、3xx 重定向、4xx 客户端问题（404 资源不存在）、5xx 服务端问题（500 服务端崩了）。

参数三种形态：路径参数（定位资源）、查询参数（问号后键值对，用于过滤/排序/分页）、请求体（POST 大段数据放 body，例：向 /api/v1/orders 发创建订单请求带用户 id 和商品列表）。

### RESTful 设计原则

两条核心：资源导向——URL 放名词（用户/订单/商品），动词用 method 表达（GET /users/123、DELETE /users/123）；无状态——每个请求必须携带服务端所需全部信息，好处是可水平扩展，代价是会话状态要自己存客户端或外部存储。路由分组与版本管理：/api/v1、/api/v2 新老并存避免改挂老客户端；gin 框架用 group 把同一资源的增删改查路由归到一起，方便维护和挂中间件。

### 中间件与 JWT 鉴权

中间件是函数，在请求到达最终 handler 前后执行，即洋葱模型——"进去的时候处理请求，出来的时候处理响应，每一层都是一个洋葱皮"；换个比喻，"一个个中间件就是流水线上的工人，从前往后传递请求，从后往前传递响应"。核心是责任链模式：每个中间件只做一件事，嵌套组合统一管理（安全防护/日志/JWT 鉴权分层）。

JWT 流程：登录验证通过后签发令牌（编码用户信息 + 签名防篡改），客户端每次请求在 header 携带，服务器中间件验签通过后把用户信息注入上下文；代码上从 authorization 字段取令牌、判空打回、验证通过后调 next.ServeHTTP() 进入下一层（Gin 里即 c.Next()）。JWT 与 RESTful 无状态原则是"天作之合"：服务端不存会话，直接解析，利于水平扩展。

### 数据模型设计

"代码再漂亮、表设计一塌糊涂也会性能差、改不动、全是 bug。"三步法：识别实体 → 梳理关系 → 建表。经典简易商城例子：User、Product、Order、OrderItem 四表，均为一对多关系，用外键表达（Order 有指向 User 的外键；OrderItem 有两个外键分别指向所属 Order 和原始 Product——不可能把整个产品信息复制一份）。设计要点：三范式了解即可，实际要因地制宜权衡性能/清晰度/复杂度；考虑索引建在什么列上；普通开发直接用 MySQL。

### 缓存与开发规范

缓存两个目的：降低延迟、减轻数据库压力。Redis 是最主流的内存缓存（五种核心数据结构点名未展开，查讲义）。开发规范：项目必用 Git 的三个理由——回溯历史可回滚、多人协作有 merge conflict 提醒防覆盖、pull request 支持代码审查；工作流 clone → checkout 新分支 → 修改提交 → PR → review → 合并。敏感信息（JWT 签名密钥、密码）不进代码仓库，用环境变量管理。CI/CD 的价值："出了问题是机器拦住的，而不是等到生产环境中才会被用户发现的。"

### Docker 容器化部署

slogan"一次构建，到处运行"。基础镜像由企业/开源发布者提供，Dockerfile 构建自己的镜像（装软件、拷代码），镜像启动后成为容器。三个核心特性：

1. **共享宿主机内核**：容器本质是宿主机进程、没有自己的操作系统——内核版本/系统调用/GPU 驱动等内核态必须与宿主机一致，但 C/C++ 库、Python 运行时、node 版本等用户态随便配；相对虚拟机毫秒级启动、占用资源少得多。
2. **镜像分层构建**：每条 Dockerfile 指令生成只读层，容器层可写；固化运行环境，解决"我电脑上能跑服务器上不行"。
3. **写时复制**：多镜像/多容器共享同一基础镜像且互不干扰，不占大量存储。

多阶段构建实例：基于 golang 基础镜像编译出二进制 → 第二阶段切换 alpine 极简 Linux 只拷二进制 + 指定端口，避免最终镜像带编译器和源码中间产物。实用提醒：docker compose 在一个配置文件定义应用/数据库/缓存等多个服务，一条指令启动整个开发环境；国内访问 Docker Hub 慢，一定要配镜像加速地址。
