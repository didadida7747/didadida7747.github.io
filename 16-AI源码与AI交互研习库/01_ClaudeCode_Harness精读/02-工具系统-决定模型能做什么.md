# 02 · 工具系统：决定模型能做什么

> 如果说主循环是心脏，工具就是四肢。本篇拆 Claude Code 的内置工具设计——这是整套 harness 里"性价比最高"的学习材料，因为你写任何 Agent 都要设计工具。

## 一、工具清单与它们的分工

Claude Code 的内置工具（以官方文档为准，随版本增减）：

| 工具 | 作用 | 设计要点 |
|---|---|---|
| Bash | 执行 shell 命令 | 万能逃生舱，但被严格引导 |
| Read | 读文件（图片/PDF也能读） | 分页、行号、单次上限 |
| Edit | 精确字符串替换 | 必须先 Read；old_string 必须唯一 |
| Write | 整文件写入 | 覆盖前也必须 Read 过 |
| Glob / Grep | 文件名/内容搜索 | 独立于 Bash 的专用搜索 |
| WebFetch / WebSearch | 取网页/搜索 | 只给结论不给全文（防上下文爆炸） |
| TodoWrite / TodoRead | 任务清单 | 把"计划"外化成可见状态 |
| Task | 派生子代理 | 见 05 篇 |
| NotebookEdit | Jupyter 编辑 | 小众但体现"专业工具专业化" |
| AskUserQuestion | 结构化提问 | 强制选项式交互，防模型瞎猜 |
| EnterPlanMode / ExitPlanMode | 计划模式切换 | 只读→审批→执行的两段式 |
| MCP 工具 | 用户自接的外部工具 | 动态注册，命名 `mcp__服务__工具` |

【总评】这个清单的形状本身就是理念：**少量工具，每个职责清晰，互相正交**。对比早期 Agent 动辄几十个工具，Claude Code 把"读"（Read/Grep/Glob）和"写"（Edit/Write）严格分开，把"搜"从 Bash 里拆出来——为什么？往下看。

## 二、五条工具设计原则（每条都有反例）

### 原则 1：返回值裁剪到"刚好够做决策"

工具结果不是越大越好。Read 有行数上限，Bash 输出会被截断，WebFetch 让一个小模型先把网页压缩成针对当前问题的摘要再返回。

【为什么】一个网页全文轻松 50K token，直接进上下文 = 立刻吃掉 1/4 窗口 + 模型注意力被稀释。**上下文是预算，工具是花预算的地方。** 你自己设计 Agent 时，90% 的上下文爆炸都来自"工具结果不做裁剪"。

### 原则 2：用"描述"做行为引导，而不是用"强制"做硬约束

去读泄露的系统提示词（07 篇），你会看到大量对工具使用的引导：

> "Do not use `sed`, `awk`, or `cat` to read files — use the Read tool instead."
> "Prefer dedicated search tools over bash `grep`."

模型有足够能力用 Bash 实现一切，但没有——因为引导 + 工具设计本身已经更优。

【为什么这样设计而不是硬禁止】硬禁止（不注册 Bash 工具）会让模型在真的需要时无路可走，陷入死循环。引导则是给模型"默认路径"，保留逃生舱。**软引导为主、硬护栏为辅**，是所有 harness 调优的日常。

【更深一层】Read 比 `cat` 好在哪？① 带行号（模型改代码需要行号做坐标）；② 分页防爆；③ 可以读图片/PDF（模型多模态）；④ 统一入口便于权限系统拦截和结果裁剪。工具的价值不在"能不能"，在**返回的信息结构和下游环节咬合得多紧**。

### 原则 3：写操作必须是"可验证的"，不信赖记忆

Edit 的设计是整个系统的精髓：必须给出 `old_string`（原文）+ `new_string`（新文），且 old_string 必须**唯一匹配**（或附带唯一性上下文）；必须先 Read 过这个文件。

【反事实推理】如果允许"给第 42 行插入 xxx"会怎样？模型对行号的记忆经常是错的（文件可能已被它自己改过），行号漂移 → 改错位置 → 越改越乱。而"原文→新文"的字符串替换，**old_string 本身就是校验**：匹配不上就报错还给模型，模型自己重新读文件。这是把"幻觉防线"内置进了工具协议。

【你能学到】设计任何"模型改状态"的工具时，都问一句：这个操作有没有内置校验？校验失败的信息能否让模型自我纠正？

### 原则 4：把高频意图升级为一等工具

TodoWrite（任务清单）、AskUserQuestion（选择题式提问）都可以用 Bash/文本凑合实现，但 Claude Code 把它们升级成结构化工具。

【为什么】① 状态外化：TODO 列表渲染在 UI 上，用户随时看到 Agent 的计划，可干预；② 结构化输入减少模型跑偏（AskUserQuestion 的选项制让"澄清需求"变成低成本动作而不是长篇大论）。**当某个行为模式足够高频、且需要展示给人看时，就该给它一个专门工具。**

### 原则 5：工具描述是提示词工程的一部分

每个工具的 JSON Schema 里的 description 字段动辄几百 token，里面全是行为规则（Bash 的描述里写着"避免用什么、路径怎么处理、输出超长怎么办"）。

【为什么】工具定义是模型唯一能"读到的说明书"。模型对工具的用法质量 ≈ 描述质量。业界流传的共识：**工具描述里一个精确的负面示例，胜过提示词里十句"请小心使用"。**

## 三、MCP：工具系统的"外挂接口"

MCP（Model Context Protocol）是 Anthropic 2024 年 11 月开源的协议，2025 年成为行业标准（OpenAI、Google、字节等都宣布支持）。

```
你的工具实现（任何语言） ──► MCP Server（stdio/SSE） ──► Claude Code ──► 模型
```

- 工具动态注册进主循环，模型视角和内置工具无差别（命名 `mcp__github__create_issue`）
- 传输层支持本地进程（stdio）和远程服务（HTTP/SSE）
- 除了 tools，还有 resources（数据源）和 prompts（预置提示词）两类原语

【为什么 MCP 重要】它把"给 Agent 加能力"从改 harness 代码变成了装插件。看懂了 02 篇你就能明白：MCP 本质上是把"工具定义 + 执行器"标准化后的远程过程调用，主循环和权限门对它一视同仁。

【我的批注】学 Agent 开发，MCP 是当下投入产出比最高的标准之一：写一个 MCP server，在 Claude Code/Cursor/Windsurf 里全能用。06 章练习题 4 会带你写一个最小的。

## 四、一张"工具设计自检表"（拿去审查你自己的 Agent）

- [ ] 每个工具职责单一吗？（一个工具干两件事 = 两个失败模式）
- [ ] 返回值裁剪了吗？超长结果怎么截、往哪截？
- [ ] 写操作有没有内置校验？校验失败信息能帮模型自纠吗？
- [ ] 工具描述里有没有：使用时机、不使用时机、负面示例？
- [ ] 这个工具失败的"姿势"优雅吗——错误信息模型读完能自己修正吗？
- [ ] 高频意图是否值得升级为一等工具？
- [ ] 有没有给模型留"逃生舱"（万能工具），还是死胡同里没有退路？

## 思考题

1. 为什么 Glob/Grep 独立成工具，而不是让模型用 Bash 的 find/grep？（提示：从权限粒度、输出格式、Windows 兼容性三个角度想）
2. Edit 的"old_string 唯一性"校验失败时，你觉得 harness 应该返回什么信息给模型？返回整个文件？还是返回所有匹配位置？
3. 假设你要给 Claude Code 加一个"运行单元测试"的专门工具，描述你会怎么写？
