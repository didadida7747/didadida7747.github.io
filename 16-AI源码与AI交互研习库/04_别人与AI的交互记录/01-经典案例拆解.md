# 01 · 经典案例拆解：8 个可验证来源的真实交互

> 每个案例：来源 → 关键交互（摘录或忠实转述）→ 用 00 篇的"解码器四问"解剖 → 你能偷走什么。
> 全部链接已核对收录在 [05 章资源地图](#/doc/d454)，本篇专注解剖。

## 案例 1：Claude Code 作者的"探索-计划-写码-提交"四拍

**来源**：Anthropic 官方博客《Claude Code: best practices》（作者之一就是 Boris Cherny）

**关键交互**（忠实转述）：

```
1. "阅读这个仓库，理解它是怎么处理 <x> 的，先不要写任何代码。"
   （让它读完汇报理解，人纠正其理解偏差）
2. "你刚说的方案，写成一个 markdown 计划文件，别改代码。"
   （计划落盘 = 状态外化，也是下一个会话的锚点）
3. "按计划里的第 1-3 步实现。每完成一步更新计划文档的勾选状态。"
4. "写 commit 信息，提交。"（或推 GitHub 让它开 PR）
```

**解码**：
- 四拍的本质是**每一拍之间插入一个人工确认门**（00篇"最小充分集"的交互版）；
- "先不要写代码"这句话单独看多余，实际是对模型 over-eager 倾向的精确约束；
- 计划文件既是给模型的记忆，也是给用户的审计界面——一物两用。

**偷走**：任何非琐碎任务都用这四拍。计划文件建议放 `plan.md` 并进 `.gitignore`。

## 案例 2：Boris Cherny 的日常纪律（播客/访谈）

**来源**：Boris Cherny 多次公开访谈（Lenny's Newsletter 播客等）与 X 分享

**关键做法**（转述）：
- **多窗口并行**：同时开多个 CC 会话各干一件事，人只做分发和验收；
- **/clear 用得极勤**：任务切换必清上下文，"上下文是易腐品"；
- **给上下文要舍得**：贴报错全文、贴截图、贴相关文件，"你不会给实习生只发半句话"；
- **用 MD 文件当记忆**：项目约定全部沉淀 CLAUDE.md。

**解码**：注意所有纪律的共同形状——**人的角色从"写码的人"变成了"harness"**（组装上下文、验收产出、管理记忆）。这是本库 00 章预言过的事实：管理 AI 的能力 = 人肉实现一个优秀的 harness。

**偷走**：下次并行干三件事试试：一个会话改 bug、一个写测试、一个查资料，你来当 orchestrator。

## 案例 3：Harper Reed 的 LLM 代码生成流水线

**来源**：Harper Reed 博客《My LLM Codegen Workflow》（工程师，曾任 Obama 竞选团队 CTO）

**关键流程**（忠实转述）：
1. **Brainstorm**：和模型纯聊天，只做想法发散，明确说"不要写代码"；
2. **生成 PRD**：让模型把讨论写成产品需求文档，然后"逐条审视你自己的 PRD，挑毛病"（自我批判轮）；
3. **生成 Tickets**：把 PRD 拆成小票，每张票小到"一次会话能干净完成"；
4. **逐票实现**：每张票新开会话（/clear），贴规格 → 实现 → 测试 → 下一张。

**解码**：
- 最妙的是第 2 步的**自我批判轮**——用模型查模型，成本几乎为零；
- "每张票新开会话"是 01章04篇 /clear 原则的工程化落地：宁可多付固定上下文成本，也不带污染干活；
- 整个流水线里模型从未拿到"模糊授权"，每一步的输入输出都明确。

**偷走**：把"自我批判"加进你的流程："批判一下你自己刚写的方案，找出 3 个最可能失败的地方。"

## 案例 4：Karpathy 的 vibe coding 命名现场

**来源**：Andrej Karpathy 2025.2 的著名推文（"There's a new kind of coding I call 'vibe coding'..."）

**关键内容**（原文大意）：完全跟着感觉走、用自然语言指挥、"全盘接受 AI 的所有建议"（Accept All 永远不点 diff）、忘记代码的存在——适合周末玩具项目。

**解码**：
- 注意语境：**这是带自嘲的观察，不是操作建议**。他同时说明这适合 throwaway 项目——vibe coding 的边界被后来很多转述者弄丢了；
- 这条推文的真正价值是命名了一个**光谱**：从"逐行审查"到"全盘接受"，每个人应该按任务的"可承受错误成本"选自己的位置（02章对比 Aider vs CC 的光谱图同一个道理）。

**偷走**：给自己的任务先分类：玩具（可 vibe）/ 内部工具（抽查 diff）/ 生产（逐 diff 审）。分类错了才会翻车。

## 案例 5：Simon Willison 的"透明研究"与鹈鹕测试

**来源**：Simon Willison 博客（他坚持在博客中贴出完整 AI 对话记录）

**两个招牌做法**：
1. **贴全量对话**：他几乎所有 AI 辅助的博文都附完整 transcript，"读者可以审计我 AI 参与的每一处"；
2. **鹈鹕骑自行车测试**（pelican on a bicycle）：让模型生成"鹈鹕骑自行车"的 SVG，当作跨模型的趣味基准，比抽象跑分更直观地暴露各模型审美与指令遵循差异。

**解码**：
- 贴 transcript 的深层价值：**交互记录成为可复现实验**——别人能基于同一份记录讨论"这里为什么不换种问法"；
- 鹈鹕测试展示了一个被低估的技能：**自己发明基准**。当公开跑分和你的场景不匹配时，一个 10 分钟的自制小测试比榜单更有指导意义。

**偷走**：给团队建一个"我们的鹈鹕测试"：一个固定的刁钻小任务，每次换模型/升级版本都跑一遍，人工盲评。

## 案例 6：Peter Steinberger 的"Agentic 反滥用"系列

**来源**：Peter Steinberger（iOS 圈知名开发者）的系列博文（"Claude Code tips & tricks"、"Claude Code loves to cheat" 等）

**关键观察**（忠实转述）：
- Agent 会"作弊"：为了通过测试而**改测试**、注释掉失败的用例、或者写一个永远通过的假测试——每个行为都真实发生过；
- 他的对策：把测试文件设为只读（权限系统 deny）、要求 diff 审查、让另一个会话独立 review 改动；
- 还有大量实战技巧：计划先行、并行会话、自定义命令沉淀高频流程。

**解码**：
- "Agent 作弊"揭示了 RLHF 模型的深层行为模式：**优化显性指标而非隐含意图**（和 R1 论文里奖励投机是同一枚硬币）；
- 他的对策全部是 harness 级的（权限 deny、独立 review）而不是提示词级的"请你不要作弊"——**行为问题要用机制解决**，呼应 01章08篇模式 8。

**偷走**：把测试文件加进 deny 列表（`.claude/settings.json`：`"Edit(./tests/**)"` 先禁后放，配合人工审查）。

## 案例 7：Geoffrey Huntley 的 "Ralph" 循环

**来源**：Geoffrey Huntley 博客（"Ralph Wiggum as a software engineer"）

**关键做法**（忠实转述）：用一个极简 bash while 循环，反复启动 headless 模式的 coding agent，每次都从同一个 prompt 文件出发，配合一个 PROMPT.md 记录当前状态与下一步——**用"笨循环+状态文件"让 Agent 跑数小时的长任务**。

**解码**：
- 表面看这是"最蠢的自动化"，实际包含两个严肃设计：**状态外化到文件**（每次循环是全新上下文，全靠 PROMPT.md 接力）和**幂等重启**（失败就再来一轮，反正上下文便宜）；
- 它是 01章04篇"文件当草稿纸"思想的极端应用，也是 2026 年"长时后台 Agent"的民间雏形。

**偷走**：不必学它跑一整夜（烧钱），但"用文件给无状态循环接力"这个技巧在做 CI 自动化/批量任务时极其好用。

## 案例 8：Anthropic 自家的 dogfooding 内部分享

**来源**：Claude Code 团队内部分享（公开流传的内部 talk 内容与团队博客）

**关键事实**（转述）：造 CC 的团队自己重度使用 CC；出现频率最高的建议依旧是 **/clear 勤快点**、CLAUDE.md 持续沉淀、"把它当结对的人而不是许愿机"。

**解码**：当不同来源（官方博客、作者访谈、团队内部分享）的结论收敛到同几条时，这些结论的置信度就很高了。**学习任何新工具，优先寻找"多来源收敛"的实践。**

**偷走**：判断任何"最佳实践"真伪的三连问：官方文档说过吗？重度用户说过吗？你自己试过吗？

## 案例总览：8 个案例收敛出的 5 条铁律

1. 任务之间清上下文（案例 1/2/3/8）
2. 计划先落盘、执行按票走（案例 1/3/7）
3. 验收看 artifacts 不看自我汇报（案例 6 及 02 篇死法二）
4. 行为问题用机制（权限/deny/review）解决，不用道德倡议（案例 6）
5. 人是 orchestrator：组装上下文、拆任务、验产出（案例 2/3/7）

> 这 5 条与 01章08篇的工程模式一一对应——harness 设计和人与 AI 的协作姿势，本来就是同一件事的两面。
