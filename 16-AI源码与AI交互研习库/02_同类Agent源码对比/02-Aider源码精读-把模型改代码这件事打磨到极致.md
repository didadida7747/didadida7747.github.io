# 02 · Aider 源码精读：把"模型改代码"这件事打磨到极致

> 仓库：`Aider-AI/aider`（Python，Apache-2.0）。作者 Paul Gauthier 从 2023 年就开始做 AI 结对编程，比 Claude Code 早两年，**很多后来成为行业共识的设计，Aider 是先行者**。
> Aider 的哲学和 CC 不同：CC 是"任务驱动"（给它一个目标），Aider 是"人机结对"（你开车它导航）。本篇讲三个它打磨最深的地方。

## 一、Edit Format：让模型用"可校验的方言"改代码

### 问题

模型改代码最容易翻车的方式：让它输出整个新文件（长、贵、易丢上下文），或让它输出 diff 格式（行号对不上、格式严格易错）。

### Aider 的答案：SEARCH/REPLACE 块

```
path/to/file.py
<<<<<<< SEARCH
def old_function():
    return 1
=======
def new_function():
    return 2
>>>>>>> REPLACE
```

在 `aider/coders/editblock_coder.py` 里，处理逻辑的核心是：
1. 用 flex 正则从模型回复里**宽容地**解析出这种块（模型输出的格式总有噪音，解析器必须容错——`flexible Heredoc` 匹配，哪怕模型漏了几个 `=` 或空格都能抓住）；
2. `replace_most_similar_chunk()`（157 行起）：一条**宽容度递增的匹配瀑布**——完全匹配 → 空白归一匹配（缩进/空格错误零风险可修）→ 丢掉模型多加的首空行（注释里留着 issue #25）→ 展开 `...` 省略块；而"编辑距离模糊匹配"作者写了却**亲手禁用**了——修"表达误差"可以，修"认知误差"不行（逐段批注见 [02b 篇](#/doc/d441)）；
3. 找不到/不唯一 → 把失败信息返回，让模型重试。

【为什么这是教科书级设计】
- **块本身是校验**：SEARCH 不匹配就失败，杜绝了"凭记忆改错地方"；
- **容错在 harness 层做**：不指望模型输出完美格式，而是把模型输出当"近似指令"再解析。**对模型宽容、对结果严格**——这是所有 LLM 工程的黄金法则；
- 后来 CC 的 Edit 工具（old_string/new_string + 唯一性校验）就是同一协议的产品化版本。

【延伸】Aider 还实现了 udiff 格式（给 GPT-4 系用）和 architect 模式（一个模型出方案、另一个模型落码——"规划者/执行者"分离的早期实践，即 CC Plan Mode 和子代理分工的思想雏形）。`aider/coders/` 下每个 coder 一个文件，可以直接对比同一问题（"怎么把模型的话变成文件修改"）的多种解法。

## 二、Repo Map：小预算装下大仓库

### 问题

上下文塞不下整个代码库，但模型又需要"全局视野"才能改得对。给什么？

### Aider 的答案（`aider/repomap.py`）

1. **tree-sitter** 解析全库，抽出符号（类/函数/方法）及其引用关系 → 一张"符号依赖图"；
2. **图排序**（PageRank 思路）：被引用多的符号 = 更重要的符号，排在前面；
3. **按 token 预算从高到低填充**：预算（如 1K-4K token）用完就停；
4. 顺手把"最近改过的文件的符号"加权（git 活动 = 你正在关注的区域）。

最终给模型的是一张"代码骨架地图"：

```
main.py:
│   def main()
│   class App
│       def run()
utils/auth.py:
│   def verify_token(token)   ← 被引用 12 次，权重高
```

【为什么这是神来之笔】它回答了"上下文该放什么"的最难场景：**不是用户告诉模型看什么，而是 harness 替模型预判什么重要**。用图算法做信息筛选，而不是无脑 RAG 向量检索——对"代码"这种结构化文本，符号图比向量库准得多。

【你能学到】RAG 不是唯一答案。**领域结构（AST/符号表/调用图）+ 经典算法（PageRank）+ 预算控制**，三件套可以解决"给模型喂什么"的很多问题。

## 三、Git 深度集成：每次修改自动 commit

Aider 默认每次 AI 改动后自动 `git commit`，commit message 由模型生成且**只描述 AI 的改动**；用 `/undo` 一键回滚到 AI 动手前。

【为什么】① AI 改坏 = 回滚成本为零；② commit 历史成为"AI 干了什么"的审计日志；③ 干净的 diff 让用户审查成本骤降。这是 03 篇"checkpoint/rewind"思想的先驱——**可撤销性是 AI 改代码的安全网**。

## 四、Benchmark 文化：把 prompt 当代码测量

Aider 维护 polyglot benchmark（多语言代码编辑测试集），每次改 prompt/edit format 都跑分对比，结果公开。

【为什么值得单独一提】大多数人调 prompt 靠"感觉这版更好"，Aider 靠数据。**你自己的 Agent 优化如果没有评测集，就是在抛硬币。** 06 章实验室的练习题 5 会让你给 toy harness 写一个最小评测。

## 五、Aider vs Claude Code：一个值得记住的对比

| 维度 | Aider | Claude Code |
|---|---|---|
| 心智模型 | 结对：你提需求它改当前文件 | 委托：你说目标它自己找路 |
| 上下文策略 | repo map + 你指定文件 | 自主探索 + 子代理 |
| 改动粒度 | 每次 edit 都 commit | 会话级 checkpoint |
| 交互 | IDE 之外（终端/切屏） | 驻留终端 |
| 适合 | 精确修改、大型库渐进改造 | 从零到一、多文件大任务 |

【我的批注】不要二选一。高手是"大任务用 CC、精细活用 Aider/IDE 内联补全"混用。理解两边的源码后你会自然形成自己的混用策略——这就是读源码的复利。

## 思考题

1. SEARCH/REPLACE 的"相似度兜底"（缩进对不上也帮模型匹配）有没有风险？什么场景下 harness 应该拒绝兜底？
2. repo map 的符号加权用了"git 最近改动"，如果仓库是多人协作、你自己只碰过一小块，这个加权会不会反而误导？怎么改？
3. 为什么 Aider 的自动 commit message 强调"只描述 AI 的改动"？（提示：人机混编的 blame 问题）
