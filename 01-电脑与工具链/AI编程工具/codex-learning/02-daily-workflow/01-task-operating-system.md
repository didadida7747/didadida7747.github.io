# Codex 日常任务操作系统

这是每次使用 Codex 都可以套用的流程。它来自橙皮书的“从需求到交付”思路，并结合本机配置和官方资料做了收敛。

## 一条主线

```text
读项目 -> 拆需求 -> 定边界 -> 小步实现 -> 验证 -> 看 diff -> 总结 -> 提交/沉淀
```

## 1. 读项目

适用：新项目、陌生目录、很久没碰的代码。

提示词：

```text
请先不要修改文件。先阅读当前项目，输出：
1. 技术栈
2. 入口文件
3. 关键目录
4. 测试/构建/启动命令
5. 风险文件
6. 你建议的第一步
```

通过标准：它给出明确文件路径和不确定项，而不是泛泛解释。

## 2. 拆需求

适用：任务超过一个文件、你自己也不确定要怎么改。

提示词：

```text
请先做需求拆解，不要修改文件。

需求：
【写你的需求】

请输出：
1. 目标
2. 涉及文件
3. 不涉及范围
4. 可能风险
5. 建议先做的最小步骤
6. 需要我确认的问题
```

通过标准：每个子任务都能单独验收。

## 3. 定边界

必须写清楚：

- 能改哪些文件。
- 不能动哪些文件。
- 是否允许安装依赖。
- 是否允许联网。
- 是否允许改配置。
- 是否要保持现有 API、路由、数据格式不变。

## 4. 小步实现

提示词：

```text
请开始小步实现。

本轮只执行第【n】步：
【具体任务】

边界：
1. 只修改【文件/目录】
2. 不新增依赖，除非先说明原因并等我确认
3. 不改公共 API
4. 修改后读回关键文件
5. 不继续做下一步
```

## 5. 验证

优先级：

1. 项目自带测试：`npm test`、`pytest`、`cargo test` 等。
2. 类型检查：`npm run typecheck`、`tsc --noEmit` 等。
3. 构建：`npm run build`、`cargo build` 等。
4. 静态检查：`npm run lint`、`ruff`、`cargo clippy` 等。
5. 没有命令时：读回关键文件 + 明确说明无法验证的原因。

不要接受这种总结：`已完成并验证`，但没有命令、输出或读回证据。

## 6. 看 diff

检查重点：

- 改动是否集中。
- 删除是否合理。
- 是否出现硬编码密钥、绝对路径、账号信息。
- 是否引入无关依赖。
- 是否修改了锁文件但没说明原因。
- 是否把格式化造成的大面积改动混进功能改动。

## 7. 总结与沉淀

让 Codex 最后输出：

```text
请总结本次任务：
1. 改了什么
2. 为什么这样改
3. 运行了哪些验证
4. 没有验证的部分
5. 风险和后续建议
6. 建议的 commit message
```

如果同样的要求连续出现 3 次，就考虑沉淀到 `AGENTS.md`、Skill 或项目模板里。
