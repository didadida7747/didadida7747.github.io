# 04 · 上下文工程：压缩、记忆与 CLAUDE.md

> Anthropic 在 2025 年的工程博客《Effective context engineering for AI agents》里说得很直白：早期大家比拼 prompt engineering（怎么措辞），现在比的是 context engineering（**每一步让模型看到什么**）。
> 本篇拆 Claude Code 的上下文管理全链路。这是全套资料里"含金量/字数比"最高的一篇。

## 一、上下文不是越大越好：一个反直觉的前提

200K 的窗口看着很大，但实际可用空间被四类东西瓜分：

```
┌───────────────────────────────────────────┐
│ 系统提示词（静态规则）          ~2-4K token │
│ 工具定义（十几个工具的schema+描述） ~5-10K+  │
│ CLAUDE.md / 环境信息           ~1-5K       │
│ ─────────── 以上是固定开销 ─────────────── │
│ 对话历史 + 工具结果（动态增长）   剩余全部    │ ← 真正干活的燃料
└───────────────────────────────────────────┘
```

固定开销就有万级 token，而且**动态部分越长，模型对它的利用率越低**（"lost in the middle"效应：长上下文中间部分的信息容易被忽略）。

【推论】上下文管理的目标不是"塞得更多"，而是"**每一 token 都值得模型的注意力**"。所有下面的机制都在为这个目标服务。

## 二、五种上下文管理机制逐个拆

### 1. CLAUDE.md：低成本、高杠杆的"常驻记忆"

三层结构：
- `./CLAUDE.md`（项目根，进 git，团队共享）：构建命令、代码规范、架构说明
- `./CLAUDE.local.md`（个人，不进 git）：个人偏好
- `~/.claude/CLAUDE.md`（全局）：跨项目的个人习惯

支持 `@path/to/file` 语法导入其他文件。对话中输入 `#` 开头的话会被引导存进 CLAUDE.md（"这个教训值得记住"的快捷方式）。

【为什么这样设计】它是把 prompt engineering 从"每次都打一遍"变成"写一次常驻"。注意官方文档对 CLAUDE.md 的建议非常克制：**短、事实性、写构建命令和规范，别写长篇大论**——因为它每次会话都要占固定预算，写多了等于给每次会话加税。

【常见误区】把 CLAUDE.md 当 wiki 写（几千字的项目介绍）。正确姿势是把它当成"新员工入职第一页"：命令 + 红线 + 三个最重要的架构事实。

### 2. Auto-compact：自动压缩

上下文接近上限时（具体阈值随版本变化，大约在九成左右），harness 自动触发一次总结：把冗长的历史压缩成结构化摘要（做过什么、改了哪些文件、当前状态、下一步），然后带着摘要继续干活。用户也可以手动 `/compact`，还能给指令（"保留所有报错信息"）。

【进阶阅读】逆向课程 analysis_claude_code 的 s08 章把这道工序还原成**固定顺序的四段流水线**（超大结果先落盘 → 旧中段归档 → 微压缩 → 全量总结，外加 API 拒绝后的反应式补救），与本篇的批注互为印证——详见 [10 篇的对照精读](#/doc/d436)。

【为什么"总结"而不"截断"】截断丢失的是最近因果链（正在修的 bug 的上下文），总结保留的是任务骨架。压缩的成本（一次额外调用）远低于"模型忘了自己在干嘛"的代价。

【你能学到】给任何长时 Agent 做设计，"压缩触发点 + 保留什么"这两个决定值千金。06 章练习题 3 就是让你亲手实现一个简化版。

### 3. /clear：比 /compact 更便宜的 reset

官方最佳实践里反复强调：任务之间用 `/clear` 清空上下文开新任务，**不要让上一个任务的残骸污染下一个**。

【为什么它比压缩更好】压缩是"有损保留"，清空是"零成本归零"。Anthropic 内部工程师分享的工作流里，"/clear 用得越勤快越好"几乎是出现频率最高的一条。

【深层原理】LLM 的上下文里混入无关历史会引发"注意力串味"（前一个任务的错误模式被当成了项目惯例）。**上下文卫生（context hygiene）是真实存在的工程概念。**

### 4. 微压缩（microcompaction / context editing）

比 auto-compact 更细的粒度：老轮次的**工具结果**（不是整段对话）被选择性清掉或替换成占位符，因为工具结果（日志、文件内容、命令输出）是上下文里最占空间、且最常过时的部分。

【为什么只清工具结果】对话里模型自己的话（它做的决策、声明）信息密度高，工具输出信息密度低且会过时（文件已经又改过三版了）。**优先丢弃可再生的信息**（文件可以重新读），保留不可再生的（模型的意图与决策）。

### 5. Subagent = 上下文的"_swap 分区"

派生一个子代理去干脏活（读 30 个文件找线索），主线只收一句结论。

【为什么这是上下文工程的大招】它是唯一一种"既扩大了信息处理量、又完全不污染主线"的手段。05 篇专讲。

## 三、记忆体系全景图

把上面所有机制按"存在哪里、活多久"排列：

```
                    会话内                    跨会话
              ┌─────────────────┐    ┌──────────────────────┐
   昂贵/主动   │ 对话历史+工具结果 │    │ CLAUDE.md（自动注入）  │
              │ auto-compact压缩 │    │ Skills（按需加载）     │
              │ microcompaction │    │ Plan 文件（用户主导）   │
              ├─────────────────┤    ├──────────────────────┤
   便宜/被动   │ TodoWrite 外化   │    │ # 快捷记忆             │
              │ 随时可查可改     │    │ Memory工具(MCP)等      │
              └─────────────────┘    └──────────────────────┘
```

【设计逻辑】记忆不是单一机制而是**频谱**：从"完全在上下文里（贵、随时可用）"到"完全在磁盘上（便宜、要主动加载）"，按使用频率和信息寿命选择存放位置。这和操作系统的存储分级（寄存器→内存→磁盘）同构。

【我的批注】这是 Claude Code 设计里最值得抄的一页：很多团队的 Agent 记忆方案只有"往向量库存对话记录"一招，缺乏这种分层视角。

## 四、上下文腐烂的三种方式（反面清单）

1. **堆积**：工具结果不裁剪、历史不清理 → 窗口塞满，早期信息出注意力区。
2. **污染**：上一个任务/一次失败尝试的残骸留在上下文里，模型把错误当事实。典型症状：模型反复回到几轮前已经放弃的方案。
3. **失真**：多轮压缩后摘要漂移（压缩丢了关键约束），模型"记得大概"却做错细节。

对应的药方分别是：裁剪与压缩、/clear 与子代理隔离、关键事实外化到文件（CLAUDE.md/Plan 文件）而非依赖对话记忆。

## 五、Anthropic 官方的上下文心法（浓缩版）

来自《Effective context engineering for AI agents》和《Claude Code best practices》：

1. 找"最小充分集"（minimal set of high-signal tokens）：别堆上下文，找信息密度最高的表达。
2. 结构化 > 散文：Markdown 标题、列表，帮助模型定位。
3. 长任务用"文件当草稿纸"：把计划写进 plan 文件，而不是指望模型记住。
4. Just-in-time 检索 > 预加载一切：Agent 用工具现查，而不是把所有可能用到的都塞进去。
5. 子代理处理探索型任务（读得多），主线保留决策型任务（想得多）。
