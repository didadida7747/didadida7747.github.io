# 07 · 系统提示词全文批注：Claude Code 的"出厂设置"

> 素材：Claude Code 2.0.0（2025-09-29 版）泄露的系统提示词完整原文，来源 `x1xhlol/system-prompts-and-models-of-ai-tools` 仓库（原文已缓存到 `07_源码仓库/_提示词原文缓存/claude-code-2.0.txt`，共 1150 行：正文约 170 行 + 15 个工具定义约 950 行）。
> 读法建议：本篇按"原文 → 批注"交替进行。**这可能是全网性价比最高的一篇提示词工程教材**——它是 Anthropic 花了无数轮 A/B 测试和真实用户数据打磨出来的。

## 0. 先看整体结构（ anatomy ）

```
1. 身份句           "You are a Claude agent, built on Anthropic's Claude Agent SDK."
2. 安全红线（×2！出现两次）
3. 求助/反馈指引
4. Tone and style   ← 篇幅最大的小节，全是"少说话"的规则
5. Proactiveness    主动性的边界
6. Professional objectivity  别当应声虫
7. Task Management  TodoWrite 的用法（含示例）
8. Doing tasks      做任务的步骤
9. Tool usage policy 工具偏好
10. <env> 环境注入  动态部分
11. Code References 行号引用规范
── 以下 950 行：15 个工具的 description + JSON Schema ──
```

【总批注】注意比例：**教它"怎么做对事"的内容不到 1/3，其余全是"约束行为"和"环境感知"**。对照 00 篇世界观 2："harness 是护栏堆，不是功能堆"——提示词就是护栏堆的门面。

## 1. 身份句：一句话里有三次迭代

```text
You are a Claude agent, built on Anthropic's Claude Agent SDK.
You are an interactive CLI tool that helps users with software engineering tasks.
```

【批注】v1.0 时代的开头是 "You are an interactive CLI tool..."，更早（2025 年初）是 "You are Claude Code, Anthropic's official CLI for Claude."。到 2.0 变成 **"a Claude agent, built on Claude Agent SDK"**——产品逻辑变了：Claude Code 从"一个 CLI 产品"变成"Agent SDK 的一个实例"。身份句是人设的锚，措辞变化背后是产品架构变化。写你自己 Agent 的提示词时，第一句话也该想清楚"它是什么物种"。

## 2. 安全红线：为什么写了两次

```text
IMPORTANT: Assist with defensive security tasks only. Refuse to create, modify, or improve
code that may be used maliciously. Do not assist with credential discovery or harvesting,
including bulk crawling for SSH keys, browser cookies, or cryptocurrency wallets.
```

这一段在正文开头出现一次，`<env>` 之后**又原样出现一次**。

【批注】两种解释（可能兼有）：① 长上下文里指令会被"稀释"，关键红线重复注入是抗遗忘手段（04 篇的上下文腐烂对策）；② 泄露文本显示的这是两次独立注入点（静态部分+动态注入层），说明红线被设计成**随环境块再次刷存在感**。无论哪种，"重要的事说两遍"在提示词工程里是被验证有效的实践。

## 3. Tone and style：一篇"闭嘴艺术"论文

这是全篇最值得逐句啃的部分。选段：

```text
A concise response is generally less than 4 lines, not including tool calls or code generated.
IMPORTANT: You should minimize output tokens as much as possible while maintaining helpfulness...
IMPORTANT: You should NOT answer with unnecessary preamble or postamble (such as explaining
your code or summarizing your action), unless the user asks you to.
```

然后是一串 few-shot 示例：

```text
<example>
user: 2 + 2
assistant: 4
</example>
<example>
user: what command should I run to list files in the current directory?
assistant: ls
</example>
```

【批注，四层意思】
1. **"4 行以内"这种可执行的具体标准 > "请简洁"这种废话**。好提示词的规则都是带数字的。
2. **为什么逼模型少说话？省的是你自己的钱和屏幕**。CLI 场景下，模型每次啰嗦都混在工具调用之间，用户要滚动阅读。输出 token 也计费。
3. **few-shot 示例选的全是"最容易被啰嗦化的场景"**：问答、给命令、指文件。示例是行为的高杠杆校准器——比形容词管用十倍。
4. 注意还有一条：`If you cannot or will not help... please do not say why or what it could lead to, since this comes across as preachy and annoying.`——**连"拒绝的说教"都禁了**。这是拿真实用户的抱怨数据喂出来的规则。

## 4. Professional objectivity：反"谄媚"条款

```text
Prioritize technical accuracy and truthfulness over validating the user's beliefs...
Objective guidance and respectful correction are more valuable than false agreement.
Whenever there's uncertainty, it's best to investigate to find the truth first rather than
instinctively confirming the user's beliefs.
```

【批注】这是针对 LLM 最臭名昭著的毛病——**sycophancy（谄媚）**：你说什么它都说"好主意！"。对编程场景尤其致命：用户的错误方案被夸，然后被忠实实现。这段话是给模型"顶撞用户"的授权书。你在用 AI 时觉得它"太顺从不敢反驳"，根子就在系统提示词有没有这一条。**自己写 Agent 提示词，这段值得整段抄。**

## 5. Task Management：TodoWrite 为什么被写进系统提示词

```text
Use these tools VERY frequently to ensure that you are tracking your tasks and giving the
user visibility into your progress.
...If you do not use this tool when planning, you may forget to do important tasks -
and that is unacceptable.
```

后面跟了两个上百行的长示例（含"边干边标记 completed"的完整示范）。

【批注】三个信息：
1. **TodoWrite 不是功能，是纪律**。系统提示词用 "VERY frequently" 和 "unacceptable" 这种强措辞逼模型养成习惯——因为实测中模型容易忘记用。
2. 深层价值（对照 04 篇）：TODO 列表是**状态外化**，既给用户可见性，又给模型自己一个"工作记忆"锚点，还天然成为压缩时的骨架信息。
3. 示例里模型每完成一小步就调一次 TodoWrite 更新状态——**把"进度可见"做成强制循环**。你的 Agent 也该这样。

## 6. Tool usage policy：偏好声明的写法

```text
- When doing file search, prefer to use the Task tool in order to reduce context usage.
- Use specialized tools instead of bash commands when possible... Read for reading files
  instead of cat/head/tail, Edit for editing instead of sed/awk...
- NEVER use bash echo or other command-line tools to communicate thoughts, explanations,
  or instructions to the user.
```

还有并行调用的规则：

```text
When multiple independent pieces of information are requested, batch your tool calls together
for optimal performance... you MUST send a single message with multiple tool calls to run the
calls in parallel.
```

【批注】
1. 第一条是 05 篇的呼应：**连"搜索该派子代理"都写进了系统提示词**——上下文经济学的规则渗透到每一层。
2. "MUST 并行调用"这条很多人没意识到：**模型会不会并行，一半靠提示词教**。并行节省的是轮次=时间=钱。
3. 禁止"用 bash echo 和用户聊天"这种条款的存在，说明模型真的这么干过（还会用注释跟用户说话）。每一条奇怪的禁令背后都是一次真实事故。**读提示词的 dirty rules = 读事故史。**

## 7. 动态注入：`<env>` 与 `system-reminder`

```text
<env>
Working directory: /tmp/claude-history-...
Is directory a git repo: No
Platform: linux
OS Version: Linux 6.8.0-71-generic
Today's date: 2025-09-29
</env>
You are powered by the model named Sonnet 4.5. The exact model ID is claude-sonnet-4-5-20250929.
```

以及用户消息里的：

```text
<system-reminder>
As you answer the user's questions, you can use the following context: ...
IMPORTANT: this context may or may not be relevant to your tasks. You should not respond
to this context unless it is highly relevant to your task.
</system-reminder>
```

【批注】
1. `<env>` 是 harness 每次会话拼接的动态块（对照 06 章实验室的 `build_system_prompt()`——一模一样的结构）。
2. `system-reminder` 的免责声明是精髓：**注入的信息要标注"可能无关"**，否则模型会把每条注入都当任务执行。信息注入也要做"信噪管理"。
3. gitStatus 快照注明"conversation 期间不会更新"——诚实标注数据的新鲜度，防止模型拿旧状态当实时事实。

## 8. v1.0 → v2.0 的删除清单（最值得玩的观察）

对比两版泄露文本（已验证）：

| v1.0 有、v2.0 删掉 | 内容 |
|---|---|
| Following conventions | "改文件前先看代码约定、检查 package.json 确认库存在" |
| Code style | "IMPORTANT: DO NOT ADD ***ANY*** COMMENTS unless asked" |
| 收尾跑 lint/typecheck | "VERY IMPORTANT: 完成后必须跑 lint 和 typecheck" |

【批注】为什么删？不是不重要了，是**模型变强后，这些行为可以靠训练内化，不再需要明文占 token**（2.0 用的 Sonnet 4.5 对工程惯例的内化好得多）。同时 v2.0 的正文改用 `##` 二级标题——它被嵌进了一个更大的"Agent SDK"提示词结构里。

这揭示了一条提示词工程的元规律：**提示词是"模型能力不足的脚手架"，模型升级后要主动拆脚手架**。你自己项目的 CLAUDE.md 也一样：每换一次更强的模型，回去删掉过时的"教做人"条款，能省一大笔 token。

## 9. 同源对照：OpenCode 抄了它多少

把 OpenCode 的 `anthropic.txt` 和 CC 2.0 并排看（原文已验证）：**Professional objectivity 整段逐字相同；Task Management 的两个示例逐字相同；`<system-reminder>` 措辞逐字相同；"file_path:line_number 引用规范"相同；"NEVER commit unless asked"相同。**

【批注】开源 Agent 直接"借"闭源标杆的泄露提示词，是最诚实的行业投票：**这些措辞是被验证有效的**。也说明提示词的护城河很浅——真正的护城河在工具系统和上下文管理（那 950 行工具定义 + 打包代码里）。

## 10. 十条可以直接抄走的规则（从原文提炼）

1. 规则带数字："4 行以内"、"最近 5 条 commit"，不写"请简洁"。
2. 用 few-shot 示例校准行为，示例要覆盖最易跑偏的场景。
3. 反谄媚条款明示："技术正确性优先于认同用户"。
4. 红线重复注入，且注明"可能无关，别响应"。
5. 工具偏好写成"用 X 而不是 Y"的对照式（Read 而不是 cat）。
6. 状态类行为（TODO）用强措辞逼成纪律 + 给完整示例。
7. 动态环境信息（cwd/git/日期）单独成块，标注新鲜度。
8. 禁令来自事故：每条 "NEVER" 都值得你问"它吃过什么亏"。
9. 并行/串行的调用规则要明说（MUST batch independent calls）。
10. 模型升级后回头删脚手架条款——提示词是活的文档。

## 思考题

1. 为什么 CC 把工具定义（950 行）也归入"系统提示词"而不是单独的配置？这对你理解"提示词=全部静态上下文"有什么启发？
2. "DO NOT ADD ANY COMMENTS"在 v1.0 存在、v2.0 删除——你认为被删的原因是"模型学会不写"还是"产品改了主意"？去找找 CC 的 changelog 或 issues 验证你的猜想。
3. 给你的 CLAUDE.md 做一次"脚手架审计"：哪些条款是为弱模型时代的它写的？
