# 03 · 权限系统：安全与效率的 tradeoff

> Agent 能读你的文件、跑你的 shell、改你的代码——权限系统就是"给多大缰绳"的控制面板。
> Claude Code 的权限设计值得逐层精读，因为它回答了一个产品级难题：**怎么让用户敢把钥匙交给 AI？**

## 一、四级信任滑块

Claude Code 的权限模式（permission modes）本质是一个信任滑块：

```
信任度低 ◄──────────────────────────────────────► 信任度高

 default          acceptEdits           plan              bypassPermissions
 每个敏感操作      文件编辑自动放行，      只读模式，          全部放行
 都弹窗确认        其他仍要确认           专注规划            (--dangerously-skip-permissions)
```

外加一条**时间维度**：每次确认都可以选"仅此一次 / 本会话都允许 / 永久写入 settings.json"。

【为什么这样设计】注意滑块上没有"完全手动"（每条命令都确认会烦死人）和没有"默认全自动"。Anthropic 的答案是：**默认保守、按操作类型分级、把信任决定变成可积累的资产**。你允许过的操作会沉淀进配置，下次不再问——权限系统跟着用户一起成长。

【对比批注】有些 Agent 产品把"全自动"当卖点（一键全自动），把风险转嫁给用户；Claude Code 反过来把"你能精确控制"当卖点。前者赢获客，后者赢留存和口碑——在企业市场尤其如此（企业要的是可审计，见下面的 settings 层级）。

## 二、settings.json 的四层层级

权限规则存放在分层的配置文件里（从高到低优先级）：

```
1. 企业托管策略        （公司统一管控，个人不可改）
2. 项目共享配置        .claude/settings.json      （进 git，团队共享）
3. 项目本地配置        .claude/settings.local.json （不进 git，个人习惯）
4. 用户全局配置        ~/.claude/settings.json     （跨项目默认值）
```

规则形如：

```json
{
  "permissions": {
    "allow": [ "Bash(npm run test:*)", "Read(~/.zshrc)" ],
    "deny":  [ "Bash(curl:*)", "Read(./.env)", "Edit(./secrets/**)" ]
  }
}
```

【为什么这样设计】三重意图：
1. **allow 让高频操作零摩擦**：把"npm test 这种安全命令"固化，确认弹窗只留给真正危险的。
2. **deny 是红线**：比如永远不许读 `.env`（密钥泄漏是 Agent 时代最常见的事故）。
3. **分层 = 组织内的权限治理**：公司禁某操作、项目允许某工具、个人偏好某习惯，三层互不打架。这个设计明显借鉴了 git 配置（system/global/local）和 IDE 的策略管理。

【你能学到】凡是要做"AI 操作真实世界"的产品，都要先画这张表：**谁在什么范围能允许/禁止什么，配置放在哪一层，谁能改哪一层。**

## 三、权限门挂在哪：工具执行前的一个函数

从主循环（01 篇）的位置看，权限门是 `execute(tu)` 之前的一个纯函数：

```
tool_use 进来 → 匹配工具名+参数模式 → 命中 deny？拒绝
                                    → 命中 allow？放行
                                    → 都没命中？问用户
```

【关键点】权限门匹配的是**工具名 + 参数模式**，不是"意图"。`Bash(npm run test:*)` 匹配的是以 `npm run test` 开头的命令。这意味着：
- 规则是可预测的（用户能精确知道自己允许了什么）
- 但也是可绕过的（模型想跑 curl 时可以写成 `npx fetch-it`——所以高危环境还需要沙箱兜底，见下节）

【设计启示】"基于意图的权限"（让模型自评风险）不可靠，"基于语法模式的权限"可审计。两层可以叠加，但不能只有前者。

## 四、Claude Code 的"权限三明治"

完整的防线是三层叠起来的：

```
第一层：权限门（配置规则 + 弹窗）   —— 精细、可审计、可被参数变体绕过
第二层：沙箱（Sandboxing）        —— OS 级隔离：文件系统白名单 + 网络代理过滤
第三层：Human-in-the-loop（diff 预览 + checkpoint/rewind）—— 事后可撤销
```

2.0 引入的 **checkpoint/rewind** 是点睛之笔：每次 Agent 动手前自动存档，`/rewind` 一键回退（代码改动可回退，bash 副作用不回退——文档明确说了这个边界）。

【为什么这个组合好】单独看每层都有漏洞（规则可绕、沙箱有逃逸面、回滚不覆盖副作用），叠起来后"犯错成本"被压到很低：**安全设计的目标不是零事故，而是让单次事故可承受、可撤销**。这是和传统安全工程一脉相承的思路（深度防御 defense in depth）。

## 五、dangerous 模式的社会学

`--dangerously-skip-permissions`（俗称 YOLO 模式）值得单独一说：它存在本身就是产品设计的一部分。

- 高手在**隔离环境**（容器/VM/一次性云主机）里用它跑长任务，效率拉满；
- 新手在**生产机**上用它 = 裸奔。

【为什么官方留着这个开关】因为一批核心用户（自动化的重度用户、CI 场景）确实需要全自动化，不给他们就会去用竞品。官方的选择是：**给出开关 + 反复警告 + 文档教正确姿势（沙箱里用）**，而不是替用户做决定。

【你能学到】做任何工具，"危险但必要的后门"的正确姿势：显式命名（名字里就带 dangerously）、文档教最佳实践、把误用成本可视化。

## 六、实操：为你自己的项目配一份权限

最小可用配置（`.claude/settings.json`，进 git）：

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run lint:*)",
      "Bash(npm run test:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ],
    "deny": [
      "Read(./.env*)",
      "Bash(git push:*)",
      "Bash(rm -rf:*)"
    ]
  }
}
```

【批注】deny 的三条对应三种最疼的事故：密钥泄漏、误推远程、误删文件。allow 的四条覆盖了 Agent 日常最高频的自检动作。花五分钟配这个，换来的是"Agent 干活时你不用盯着弹窗"。

## 思考题

1. 为什么权限门放在工具执行前而不是模型请求后？（如果放在请求后，会损失什么？）
2. checkpoint/rewind 为什么选择"不回滚 bash 副作用"？如果一定要回滚，需要付出什么？
3. 你的工作里，哪些操作应该进 deny 列表？（真的去写一下，这是本篇最重要的练习）
