# 项目实录 · 两模型辩论达共识（Multi-Agent Debate）

两个不同的 LLM 先**独立作答**，再**互评修订**若干轮，最后由**裁判模型**（或一致性检查）裁决——验证"多模型辩论能否提升答案质量"。基于 [CrewAI](https://docs.crewai.com/) 框架，用 [uv](https://docs.astral.sh/uv/) 管理环境。本文分两部分：上半是项目说明，下半是搭建复盘。

## 它解决什么问题

单模型有"幻觉"和"思维定势"，两个训练数据不同的模型错误往往不重合：独立作答保留多样性，互评暴露对方漏洞，从而逼近正确答案。

> 学术出处： Du et al., *Improving Factuality and Reasoning in Language Models through Multiagent Debate* (2023)

## 快速开始

```bash
# 0. 前置: 已安装 uv（也可全局安装）

# 1. 配置 API key
cp .env.example .env      # Windows: copy .env.example .env
# 编辑 .env，填入两个模型的真实 key（两个模型必须不同！）

# 2. 自检端点连通性（秒级，不花 token）
uv run check_config.py

# 3. 跑一场辩论
uv run debate.py "9.11 和 9.9 哪个大？"
uv run debate.py "量子纠缠能否超光速传递信息？" --rounds 3
```

## 流程图

```
问题 ──┬─→ 模型A 独立作答 ─┐
       └─→ 模型B 独立作答 ─┤
                           ▼
              互评修订 × N 轮（A、B 各自看对方答案）
                           ▼
                 答案一致？──是──→ 共识 ✅
                           │否
                           ▼
                     裁判模型 裁决 🏁
```

## 成本提示

一场 2 轮辩论 ≈ 5~6 次 LLM 调用。用 `gpt-4o-mini` + `deepseek-chat` 这类便宜模型练手，单场成本通常不到 0.1 元。

## 常见问题

- **两边答案永远不一致怎么办？** 看裁判的说理；也可换更"强"的模型当裁判（在 .env 配 JUDGE_*）。
- **AutoDL 实例每次重启 IP 会变** → 改 .env 里 BASE_URL 即可，代码不用动。
- **想加第三个辩手？** 复制 build_debater 改名，往 run_debate 里加一路独立作答即可（留给你的练习）。

## 已知限制

- 共识 ≠ 正确：两个模型可能达成一致的错误答案（shared blind spot），裁判只能缓解不能消除。
- `norm()` 的一致性判断是字符串级近似，语义一致但措辞不同的答案会被判"不一致"交给裁判——这是保守方向的误差，可接受。

## 技术栈总览

| 组件 | 选型 | 为什么是它 |
|---|---|---|
| 语言 | Python 3.12.x | CrewAI 要求 ≥3.10 且 <3.14；太新的 3.14 alpha 不兼容 |
| 包管理 | uv | 新一代包管理工具；解析依赖快，`uv.lock` 锁定全部传递依赖保证可复现 |
| 多 agent 框架 | CrewAI | 原计划第一名的 AutoGen 已进维护模式，MAF 更重；CrewAI API 最简，适合第一个项目 |
| 模型接口 | LiteLLM（CrewAI 内置） | 一个 `model` 字符串 + `base_url` 通吃 OpenAI/DeepSeek/vLLM 自建端点 |
| 配置 | python-dotenv | `.env` 存 key，`.env.example` 进仓库当模板——key 永不进代码 |

## 架构与数据流

```
.env ──→ make_llm(tag) ×3 ──→ Agent(A, B, Judge)
                                    │
        ┌───────────────────────────┘
        ▼
  [第0步] Crew(独立作答A) ‖ Crew(独立作答B)     ← 两个独立 Crew，互不可见
        ▼
  [1..N轮] Crew(互评修订A) ‖ Crew(互评修订B)    ← prompt 里注入对方最新答案
        ▼
  norm(A)==norm(B)? ──是──→ 共识
        │否
        ▼
  Crew(裁判裁决) ──→ verdict
        ▼
  results/<时间戳>.json  ← 全程记录，可回放
```

关键设计决策：

- **为什么独立作答用两个独立 Crew 而不是一个 Crew 两个 Task？** 一个 Crew 里的 Task 会按顺序共享上下文，后跑的会"偷看"先跑的输出——独立性就没了。多辩论文献里多样性是收益来源，第 0 步必须隔离。
- **为什么用函数式 prompt 模板而非 CrewAI 的 hierarchical process？** hierarchical 会自动指定一个 manager agent，行为不透明且多花 token；显式模板让每一轮注入什么、模型看到什么完全可控、可调试。

## 核心代码走读

三段最值得精读的代码（都在 `debate.py`）：

**a) `norm()` —— "什么算达成共识"**

```python
def norm(text: str) -> str:
    t = extract_final_answer(text)          # 先抽 "最终答案:" 那一行
    return re.sub(r"[\s，。、,.:：;；!！?？'\"]+", "", t).lower()
```

一致性判断是这个系统最容易糊弄过去的地方。这里故意做得**保守**：只做字符串级归一化，语义相同但措辞不同的答案会被判"不一致"送去裁判——宁可多花一次裁判调用，不假报共识。

**b) `CRITIQUE_TMPL` —— 让模型"认错但不跪"**

模板里明确写了"如果你仍认为自己对，坚持并说理"。没有这句，弱模型会无条件附和强模型（sycophancy，谄媚效应），辩论退化成"谁强听谁的"，多样性收益归零。

**c) `make_llm()` —— 一套配置通吃所有供应商**

```python
LLM(model=model, base_url=base_url, api_key=..., temperature=0.7)
```

`deepseek/deepseek-chat` 走 DeepSeek 官方；`openai/Qwen2.5-72B` + 自建 vLLM 地址走 vLLM。模型即配置，代码零改动。

## 踩坑记录

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | Git Bash 多行 export 断行 | `export: -LsSf not a valid identifier` | 每条 export 单独一行；Windows 下 shell 语法差异要留意 |
| 2 | curl schannel 证书吊销检查失败 | `CRYPT_E_REVOCATION_OFFLINE` | 换 PowerShell 的 `irm \| iex` 安装脚本，同一网络环境行为不同 |
| 3 | 系统 Python 是 3.14 alpha | CrewAI 装不上 | 用 `uv python install 3.12` 让 uv 管理独立解释器，不碰系统 Python |
| 4 | C 盘空间顾虑 | uv/Python/venv 默认装 C 盘 | `UV_INSTALL_DIR`/`UV_PYTHON_INSTALL_DIR`/`UV_CACHE_DIR` 三个环境变量全部重定向到数据盘 |
| 5 | 官方 PyPI 下载龟速 | pythonhosted.org ~160KB/s，35 分钟下不完 crewai 依赖树（340MB+） | `[[tool.uv.index]]` 写入清华 TUNA 镜像后几分钟装完。**国内用 Python 工具链第一课：先配镜像** |

## 优化方向 & 练习建议

按难度排序：

1. **入门**：把 `--rounds` 改成 1 和 3 各跑同 5 道题，对比共识率变化（自己观察实验）
2. **入门**：加第三个辩手（前文"常见问题"里有提示）
3. **进阶**：引入 Self-Consistency——每边独立采样 3 次取多数，再辩论
4. **进阶**：裁判改为先给评分 rubric 再裁决，观察裁决质量变化
5. **挑战**：两辩手换成"生成者 vs 批评者"协作模式，对比辩论模式的优劣

## Prompt 工程要点

- 角色设定越具体，行为越稳定（"严谨的专家顾问" + 明确的认错/坚持规则）
- 输出格式约束（"最终答案:"单独一行）是程序解析的前提——**给模型的任务要为下游解析设计**
- 负面指令（"不要假设存在其他回答者"）比正面指令更易被忽略，重要约束要放在 prompt 尾部再强调

5. 一场 2 轮辩论最少、最多各多少次 LLM 调用？（答：最少 4 次——第 1 轮互评后就一致，跳过裁判；最多 7 次——独立 2 + 两轮互评 4 + 裁判 1）
